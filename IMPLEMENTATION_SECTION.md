# Implementation

This section describes the implementation details of our hybrid DPO training framework for multi-hop knowledge graph reasoning. Our system implements a three-stage pipeline that integrates similarity-based neighbor selection, visual graph representations, and direct preference optimization to train language models for knowledge graph reasoning tasks.

## 3.1 System Architecture

Our implementation follows a modular three-stage architecture consisting of data preparation, DPO training, and evaluation. The data preparation stage processes raw knowledge graph triples from JSONL format into hybrid training examples that combine textual prompts with optional visual graph representations. The training stage fine-tunes language models using Direct Preference Optimization (DPO) through the TRL (Transformer Reinforcement Learning) library to learn preferred reasoning patterns. The evaluation stage measures model performance on link prediction and multi-hop question answering tasks using multiple metrics.

The implementation is built using Python 3.10+ with PyTorch for model training, Hugging Face Transformers for model loading and tokenization, and the TRL library for DPO training. The system supports both CPU and GPU execution, with default configurations using GPT-2 for accessibility on standard hardware and extended configurations supporting larger models such as Mistral-7B-Instruct for improved performance.

## 3.2 Data Preparation Pipeline

The data preparation pipeline begins by loading knowledge graph triples from JSONL format, where each line contains a JSON object with head, relation, and tail fields. The triples are parsed and stored as tuples (head, relation, tail). An adjacency list representation is constructed to enable efficient neighbor traversal, where each entity maps to a list of (relation, neighbor) pairs.

For each triple (h, r, t), we construct a reasoning task by generating a textual prompt. The prompt format consists of a question followed by relevant KG triples. Specifically, the question is formulated as "Question: Given the KG snippet, what is the relation between {h} and {t}?" followed by a "Relevant KG triples:" header. Each relevant triple is formatted as "- ({head}) -[{relation}]-> ({tail})" on a separate line, and the prompt concludes with "Answer:". The chosen response is set to the relation r from the original triple, while the rejected response is set to the string "unknown". This pair structure enables DPO training where the model learns to prefer the correct relation over an incorrect one.

When SimCSE-based neighbor selection is enabled through the use_sns flag, the system gathers one-hop neighbors of both the head entity h and tail entity t from the adjacency list. These candidates are de-duplicated by neighbor ID, keeping the first relation encountered for each neighbor. The system then uses a pre-trained SimCSE model, defaulting to "princeton-nlp/sup-simcse-bert-base-uncased", to encode the query text and candidate neighbor texts. The query text is constructed as "{h_text} {r} {t_text}" where entity texts are retrieved from an optional entity text mapping file (JSONL format with id and text fields). If entity texts are not provided, the entity IDs themselves are used. Cosine similarity is computed between the query embedding and each candidate embedding. Candidates are filtered by a configurable similarity threshold (default 0.0) and the top-k most similar neighbors are selected (default k=5). Triples are constructed from the selected neighbors, ensuring the anchor triple (h, r, t) is always included in the selected set. If the anchor triple is not already present after ranking, it is inserted at the beginning of the selected list.

The dataset is randomly shuffled using Python's random module with a configurable seed (default 42) before splitting into train, validation, and test sets. The default split ratios are 80% for training, 10% for validation, and 10% for testing, though these ratios are configurable and must sum to 1.0. The shuffling ensures random distribution across splits while maintaining reproducibility through the fixed seed. Each example is assigned to exactly one split based on its position in the shuffled index list.

Graph visualizations are generated using NetworkX for graph construction and Matplotlib for rendering. The visualization process constructs a directed multigraph (NetworkX MultiDiGraph) from the selected triples, where each triple (h, r, t) becomes an edge from h to t with label r stored as an edge attribute. A spring layout algorithm (NetworkX spring_layout) is applied with a fixed random seed (42) for deterministic positioning across runs. The layout uses 30 iterations for speed optimization. Nodes and edges are rendered without labels (with_labels=False) for efficiency during bulk rendering, with node size set to 400. The visualization is saved as a PNG image with 100 DPI resolution using Matplotlib's savefig function. The image path is stored in each training example's JSON object under the "image" field, with the path relative to the output directory's images subdirectory. The visualization step is optional and can be disabled through the no_images flag. When enabled, rendering can be throttled using the max_images parameter (default 100) to control computational cost for large datasets. Parallel rendering is supported through a configurable number of worker processes using Python's ProcessPoolExecutor, with the default being serial execution (num_workers=0).

Each training example is saved as a JSON object in JSONL format with four fields: "prompt" containing the formatted question and triples, "chosen" containing the correct relation, "rejected" containing "unknown", and "image" containing the path to the graph visualization if rendering is enabled. Examples are written to separate files for train, validation, and test splits.

## 3.3 DPO Training Framework

The DPO training framework uses the Hugging Face Transformers library to load pre-trained causal language models. The default configuration uses GPT-2, which can be overridden to use any causal language model available in the Hugging Face model hub. Models are loaded using AutoModelForCausalLM.from_pretrained with automatic dtype detection (torch_dtype="auto"). Gradient checkpointing is enabled by default to reduce memory consumption, which is particularly important for larger models.

The tokenizer is loaded using AutoTokenizer.from_pretrained with the fast tokenizer enabled. The tokenizer is configured with right-side padding (padding_side="right") for batch processing and right-side truncation (truncation_side="right") to handle long sequences. If the tokenizer does not have a pad token defined, the end-of-sequence token (eos_token) is used as the padding token, and the model's pad_token_id is set accordingly.

Training data is loaded using the Hugging Face datasets library from JSONL files. The dataset is loaded with separate "train" and "validation" splits. Each example in the dataset is mapped through a _prepare_pairs function that extracts the prompt, chosen, and rejected fields from the JSON objects. These three fields are the required inputs for DPO training.

DPO training is implemented using the TRL library's DPOTrainer class. The training configuration is specified through TRLDPOConfig with the following parameters: output directory for saving checkpoints, per-device batch sizes for training and evaluation (default 4), number of training epochs (default 2), learning rate (default 5e-6), gradient accumulation steps (default 4), logging steps (default 10), save steps (default 500), warmup ratio (default 0.03), learning rate scheduler type (default "cosine"), optional DeepSpeed configuration path, beta parameter for DPO (default 0.5), maximum sequence length (128 tokens), maximum prompt length (64 tokens), and reference_free set to True. The reference_free=True setting means that no separate reference model is maintained, and the DPO loss is computed using the current model state.

The DPOTrainer is initialized with the model, no reference model (ref_model=None), the training and validation datasets, the tokenizer as the processing_class, and the training arguments. The trainer.train() method is called to execute the training loop. After training completes, the model is saved using trainer.save_model() to the specified output directory, and the trainer state is saved using trainer.save_state() to preserve training metrics and state information in trainer_state.json.

Reproducibility is ensured through the use of fixed random seeds. The seed is set using transformers.set_seed() with the seed value from the data configuration (default 42). This seed controls random number generation during training, including data shuffling, dropout, and other stochastic operations.

## 3.4 Evaluation Framework

The evaluation framework consists of three scripts for different evaluation tasks. The multi-hop question answering evaluation script (eval_multihop_qa.py) loads test examples from a gold JSONL file and predictions from a predictions JSONL file. The gold file contains examples with either an "answer" or "chosen" field containing the correct relation label. The predictions file contains examples with a "prediction" field containing the model's predicted relation. Accuracy is computed by comparing predicted relations to gold relations using case-insensitive string matching after stripping whitespace. The accuracy is calculated as the number of correct predictions divided by the total number of examples.

The comprehensive evaluation script (comprehensive_eval.py) provides additional metrics beyond simple accuracy. It computes macro-averaged precision, recall, and F1 scores across relation types. For each relation type, true positives, false positives, and false negatives are counted. A prediction is a true positive if it matches the gold label, a false positive if it is predicted but incorrect, and a false negative if it is the gold label but not predicted. Precision, recall, and F1 are computed for each relation type, and then macro-averaged across all relation types. Per-relation accuracy is also computed by counting the number of correct predictions for each relation type divided by the total number of examples for that relation type. The script also performs error analysis by identifying all incorrect predictions and recording the predicted relation, gold relation, and a truncated version of the prompt (first 200 characters) for each error case.

The link prediction evaluation script (eval_link_prediction.py) evaluates the model's ability to rank candidate tail entities. The script loads gold triples from a JSONL file and predictions from a predictions JSONL file. The predictions file contains examples with a "tail_rank" field indicating the rank of the correct tail entity in the model's ranked list of candidates. Mean Reciprocal Rank (MRR) is computed as the average of the reciprocal ranks, where the reciprocal rank for a query is 1 divided by the rank of the correct answer. Hits@K (default K=10) is computed as the fraction of queries where the correct answer appears in the top K ranked candidates.

All evaluation scripts output results in JSON format for easy parsing and integration into analysis pipelines. The comprehensive evaluation script also supports saving detailed results to a JSON file including overall metrics, per-relation statistics, and error cases.

## 3.5 Implementation Details

The system uses a hierarchical configuration structure defined through Python dataclasses. The HybridConfig class aggregates configurations from five sub-configuration classes: ModelConfig for model-related settings (base model path, LoRA parameters, gradient checkpointing), DataConfig for dataset-related settings (file paths, split ratios, seed values), SNSConfig for SimCSE-related settings (model name, top-k, similarity threshold), VisualConfig for image rendering settings (enable flag, layout type, DPI), and DPOConfig for training hyperparameters (beta, epochs, batch sizes, learning rate, etc.). Configuration can be overridden programmatically through nested dictionaries that match the dataclass structure, enabling flexible experimentation without code modifications.

To ensure reproducibility and efficiency, the system implements several mechanisms. All random operations use configurable seeds (default 42) for deterministic behavior. SimCSE embeddings can be cached to disk in NPZ format to avoid recomputation across runs. The embedding cache stores entity IDs as keys and their corresponding embedding vectors. Model checkpoints are saved at regular intervals (default every 500 steps) and at the end of training. Training state including optimizer state, learning rate schedule, and random number generator state is saved in trainer_state.json for resuming interrupted training.

The implementation includes several optimizations for scalability. Gradient accumulation enables effective large batch sizes with limited memory by accumulating gradients across multiple forward passes before performing a backward pass. Gradient checkpointing reduces memory footprint at the cost of increased computation by trading compute for memory. Graph visualizations can be rendered in parallel using Python's ProcessPoolExecutor with a configurable number of worker processes. The max_images parameter limits the number of images generated, reducing computational cost for large datasets. Optional DeepSpeed integration enables distributed training and memory optimization for large models through configuration files.

The codebase is organized into modular components. The src directory contains core functionality: config.py for configuration dataclasses, kg_data.py for KG data loading and processing utilities, prompting.py for prompt construction and formatting, sns_ranker.py for SimCSE-based neighbor ranking, kg_visualize.py for graph visualization rendering, and hybrid_dpo.py for DPO training entry point and utilities. The scripts directory contains executable scripts: prepare_hybrid_dataset.py for the dataset preparation pipeline, eval_multihop_qa.py for multi-hop QA evaluation, eval_link_prediction.py for link prediction evaluation, and comprehensive_eval.py for comprehensive evaluation with multiple metrics. This modular structure enables easy extension and maintenance while keeping components decoupled and testable.

## 3.6 Integration with Existing Frameworks

Our implementation integrates components from three existing frameworks while adapting them for knowledge graph reasoning tasks. From SNS (Similarity-based Neighbor Selection), we adapt the SimCSE-based neighbor ranking approach. However, instead of applying it to graph nodes in citation networks, we apply it to knowledge graph entities and relations. The ranking mechanism uses the same cosine similarity computation and top-k selection, but operates on KG triples rather than graph edges.

From GITA (Graph to Image-Text Integration), we incorporate graph visualization techniques. We use NetworkX and Matplotlib for rendering, similar to GITA's approach, but focus specifically on knowledge graph subgraphs rather than general graphs. The visualization serves the same purpose of providing visual grounding for multi-modal reasoning, but is tailored to the structure of knowledge graphs.

From GraphWiz (Graph Reasoning LLM), we extend the DPO training framework. We use the same TRL DPOTrainer and DPO loss formulation, but adapt it for knowledge graph domains. The key adaptation is the use of hybrid text+visual prompts specific to KG reasoning tasks, where the textual component includes KG triples and the visual component shows graph structure.

Beyond integration, our implementation adds several novel contributions. The dual-stage caching system ensures deterministic reruns across different machines through embedding caches and state persistence. The HPC-aware rendering workflow includes throttling mechanisms (max_images parameter) and parallel processing support for efficient image generation at scale. The comprehensive evaluation framework provides multiple metrics (accuracy, precision, recall, F1, MRR, Hits@K) and error analysis capabilities that extend beyond the evaluation tools in the original frameworks.
